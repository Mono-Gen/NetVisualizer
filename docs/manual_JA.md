# NetVisualizer 操作マニュアル

**対象読者**: ネットワーク初学者  
**バージョン**: 0.9.1

---

## はじめに

NetVisualizer（ネットビジュアライザー）は、TCP/IPネットワークの仕組みを目で見て、手で動かしながら学べる教育用シミュレータです。

このツールを使うと、以下のことができます。

- PC やサーバー、スイッチ、ルーターなどをキャンバス上に配置して、仮想ネットワークを作る
- パケット（データのかたまり）が宛先に届くまでの経路をリアルタイムで可視化する
- ICMP（Ping）、TCP、UDP、DHCP、DNS、IGMP（マルチキャスト）など、主要なプロトコルの動作を体験する
- 設定ミス（サブネットマスク間違い、ゲートウェイ未設定など）がどのような通信障害を引き起こすかを安全に学ぶ

> **ポイント**: 実際のネットワーク機器やルール（RFC）に忠実な動作をシミュレートしています。ここで学んだことは、実際のネットワーク構築に直接役立ちます。

### 1.1 モードの切り替え

| ボタン | モード | できること |

| `+ Design` | デザインモード | ノードの配置・削除・接続、IPアドレスの設定 |
| `▶ Simulate` | シミュレーションモード | パケット送信、プロトコル動作の観察 |

> **重要**: デザインモードで正しくネットワークを構成してから、シミュレーションモードに切り替えましょう。

### 1.2 テーマ（ライト／ダーク）

サイドバー下端の3つのボタンで、**Auto**（OSの設定に合わせる）・**Light**・**Dark**を切り替えられます。選択はこの端末に記憶されます。

### 1.3 言語（日本語／English）

サイドバー下端の **日本語 / EN** ボタンで、画面の言語を切り替えられます。初回はブラウザの言語設定に合わせ、以降は選択がこの端末に記憶されます。プロトコル名（ARP、ICMP、DHCP など）は訳しません。

### 1.4 作業内容は自動で保存されます

組み立てた機器とケーブルは、**このブラウザに自動で保存**され(外部へは送られません)、次に開いたときに復元されます。ARPテーブル・MACテーブルなどの学習した情報は保存しないので、いつも、まっさらな状態から始まります。**すべて消去**(またはサンプルの読み込み)をすると、保存内容も置き換わります。ブラウザが保存を許可しない環境でも、アプリは動きます(記憶できないだけです)。

### 1.5 キャンバスの動かし方

| やりたいこと | 操作 |

| **全ての機器を一度に見る** | **全体表示**ボタン |

背景の方眼も、表示に合わせて動き、拡大縮小します。サンプルを読み込んだとき、または「すべて消去」を押したときは、表示が最初の位置に戻ります。

## 第2章　ネットワークを作る（デザインモード）

### 2.1 ノードの種類

| アイコン | 種別 | 役割 |
|----------|------|------|
| 🖥 PC | エンドホスト | ネットワーク通信を発生させる端末 |
| 🗄 Server | サーバー | Webサービス・DNS・DHCP等を提供 |
| 🔀 Switch | L2スイッチ | MACアドレスを学習して転送するL2機器 |
| 🔁 Router | ルーター | 異なるネットワークをつなぐL3機器 |
| 📡 Hub | ハブ | 全ポートにパケットをコピーする旧式機器 |

### 2.2 ノードを配置する

1. デザインモードで、サイドバーの部品を**キャンバスへドラッグ＆ドロップ**して、置きたい場所に配置します。
   （部品をクリックしても追加できます。その場合は空いている場所に自動で配置されます。）
2. キャンバス上でノードをドラッグして位置を調整します。

### 2.3 ノードを設定する

ノードをクリックして選択すると、左ペインに設定パネルが開きます。

#### IPアドレスの設定

| 設定項目 | 説明 | 例 |
|----------|------|----|
| IP Address | このノードのIPアドレス | `192.168.1.10` |
| Subnet Mask | サブネットマスク | `255.255.255.0`（/24） |
| Gateway | デフォルトゲートウェイ（別サブネットと通信する場合必須） | `192.168.1.1` |
| DNS | 名前解決に使うDNSサーバーのIPアドレス | `192.168.2.20` |

> **入力チェック**: 設定パネルでは、入力中に、間違っていそうな箇所を指摘します。IPv4として正しくないアドレス、正しくないサブネットマスク、ネットワークアドレスやブロードキャストアドレス、別のインターフェースと重複しているIPアドレス、同じネットワークの外にあるゲートウェイなどです。入力は止めません。何が悪いか、どう直すかを、文で示します。

> **用語解説**:
> - **IPアドレス**: ネットワーク上の住所。郵便番号のようなもの。
> - **サブネットマスク**: 「同じネットワーク内の仲間かどうか」を判断するための値。
> - **ゲートウェイ**: 別のネットワークへ行くための出口（玄関）にあたるルーターのIPアドレス。

### 2.4 ノード同士をつなぐ（リンクの作成）

1. 各機器の下辺に、**ポート**が小さな丸で表示されます。中抜きの丸は空きポート、塗りつぶしの丸は接続済みです。ポートにマウスを重ねると、名前・IP・MACが表示されます。
2. **空きポートから、別の機器の空きポートまでドラッグ**して放すと、**リンク（LANケーブル）**が作成されます。ドラッグ中は接続できるポートが緑で強調されます。**Esc**で取り消せます。
3. スイッチ・ハブ・ルーターのポート数は、機器を選択して設定パネルの **+ Add Port** / **Remove** で変更できます。接続中のポートを削除すると、そのケーブルも削除されます（確認ダイアログが出ます）。

### 2.5 正しいトポロジーの例

```
[PC 1] ─── [Switch] ─── [Router] ─── [Server]
 192.168.1.10    L2転送  192.168.1.1/192.168.2.1  192.168.2.20
  /24                     GW:192.168.1.1→               /24
```

### 2.5a 削除と右クリックメニュー

- **ケーブルの削除**: ケーブルをクリックして選択（黄色になります）し、**Delete**キーか、中央の**×**ボタンで削除します。
- **機器の削除**: 機器を選択して**Delete**キー、または設定パネルの**Delete device**で削除します。接続中のケーブルも一緒に消えます（確認ダイアログが出ます）。
- **右クリックメニュー**（デザインモード）: 空白を右クリックするとその位置に機器を追加できます。機器は「設定を開く／ポート追加／機器の削除」、ポートは「ケーブルを外す／ポート削除」、ケーブルは「ケーブルの削除」です。シミュレーションモードでは、機器を右クリックしてARP／MAC／DNSテーブルをクリアできます。
- キーボード: 機器またはケーブルを選択して**Shift+F10**（またはメニューキー）で同じメニューが開きます。**Esc**で閉じます。

### 2.6 サンプルトポロジーを読み込む

サイドバー下部の **Load a sample**（両モードで利用可）から、用意済みのネットワークを読み込めます。サンプルにマウスを重ねると、試すことが表示されます。

| サンプル | 試すこと |
|----------|----------|
| 1. Basic LAN | PC 1 から `10.0.0.2` に Ping し、ARP→ICMP の流れを観察 |
| 2. Two Networks via Router | PC 1 から `192.168.2.10` に Ping し、ゲートウェイへのARPを観察 |
| 3. IGMP Snooping | Receiver 1 で `239.1.1.1` に Join し、Sender から `239.1.1.1` へUDP送信 |
| 5. NICが2つのPC | PC 1 から `192.168.1.20` と `192.168.2.20` に ping し、パケットがどちらのNICから出るかを観察 (ログの**経路**の行) |
| 4. Switch Loop (Broadcast Storm) | PC 1 から `10.0.0.2` に Ping し、パケット数が爆発的に増える様子を観察。一時停止でMACテーブルの書き換わりを確認し、3本のうち2本のケーブルを外して収束させる |

> 読み込むと現在のトポロジーは置き換えられます（キャンバスが空でない場合は確認ダイアログが出ます）。

## 第3章　通信を試す（シミュレーションモード）

`▶ Simulate` ボタンを押してシミュレーションモードに切り替え、通信させたいノードをクリックします。

### 3.0b 色の見方

色は一貫したルールで使われているので、ひと目で状況を把握できます。

- **プロトコルごとに1色**: ARP・ICMP・TCP・UDP・DNS・DHCP・mDNS・IGMP には、それぞれやわらかい色が割り当てられています。パケットの丸、パケットログのプロトコル列、対応するテーブル（ARPテーブル、DNSキャッシュ、TCPソケット、IGMP Snooping）で、同じ色が使われます。キャンバス右下の**パケットの色**の凡例で確認できます。パケットには必ず文字のラベルも付くので、色だけが手がかりになることはありません。
- **赤はエラーだけ**: 赤はエラーにだけ使われます。ほかの状態は、記号と文字（↑送信、↓受信、⊘破棄）で表します。
- **機器はモノトーン**: PCやスイッチは形（アイコン）で見分けるので、色はプロトコルと状態のために使われます。

### 3.0a ブロードキャストストーム

スイッチ同士がループ状につながっている（例: 2台のスイッチを複数本のケーブルでつなぐ）と、ブロードキャストが輪の中でコピーされ続け、飛行中のパケット数が爆発的に増えます。実際のネットワークでも、これで通信が止まることがあります。

NetVisualizerでは、この現象をあえて起こして観察できます。再生コントロールの **通信中のパケット** がパケット数です。画面が固まらないよう同時に飛べるパケットは最大300個で、超えた分は破棄され、**Broadcast storm** の警告が出ます。一時停止すると、スイッチのMACテーブルで同じMACがポート間を行き来する様子を確認できます。止めるには、デザインモードでループがなくなるまでケーブルを外すか、警告の **Clear all packets** を押します。

### 2.7 NICを複数持つPC・サーバー

PCとサーバーは、最大**4つのNIC**(ネットワークカード)を持てます。機器を選び、設定パネルの **+ ポート追加** を押して、NICごとにIPアドレスとサブネットマスクを設定します。サンプル「5. NICが2つのPC」で試せます。

**送信に使うNICの選ばれ方** — NICを複数持つ機器が、宛先へ送るとき(Ping・UDP・TCP)は、次の順でNICを決めます。

1. **宛先を含むネットワーク**を持つNICのうち、**プレフィックスが最も長い**もの(例: /16 より /24)。
2. 同じなら、**メトリック**が小さいNIC(設定パネルでNICごとに設定。既定は100で、小さいほど優先)。
3. それも同じなら、**一覧で先頭に近い**NIC。乱数ではありません。同じ構成なら、いつも同じ結果になります。
4. どのNICのネットワークにも宛先が含まれなければ、有効な**デフォルトゲートウェイ**を持つNICを使います(メトリックが小さい順、同じなら先頭に近い順)。

この判断は、ログに**経路**の行で出ます。例: `経路: 192.168.2.20 は eth1 から送信 (直接つながったネットワーク /24、メトリック 100)`。同点のときの動きを見るには、2つのNICを同じネットワークにして、片方のメトリックを変えてみてください。

> WindowsやLinuxの動作を単純化したモデルです。実際のOSにあるポリシールーティングや、メトリックの自動計算は再現していません。

DHCP・mDNS・マルチキャストは宛先がないので、コマンドパネルの **送信NIC** で選んだNICを使います(既定は、IPアドレスを持つNICのうち、メトリックが最小のもの)。

### 3.0 再生コントロール（一時停止・ステップ・速度）

キャンバス下部中央のコントロールで、パケットの流れをゆっくり確認できます。

- **Pause / Resume**: パケットの移動を止めます。IGMP SnoopingのエイジングやDHCPリースなどのタイマーも停止中は止まるため、テーブルのエントリは消えません。
- **Step**: 次のパケット到着まで進めます（例: ARP Request → ARP Reply → ICMP Echo Request）。実行中に押すと、先に一時停止します。通信中のパケットが無いときだけ押せません。pingを最初のパケットから追うには、送る前に Pause を押します。
- **Speed**: 0.25x〜4x。

デザインモードに切り替えると、自動的に再開されます。

### 3.1 Ping（ICMP Echo Request/Reply）

**Pingとは**: 「相手に届くか？」を確認する最も基本的な疎通確認ツールです。

#### 操作手順

1. 送信元のノードをクリックして選択します。
2. 左ペインの「〇〇 への操作」欄の「宛先」に、**宛先**（`192.168.2.20` のようなIPアドレス、またはホスト名）を入力します。
3. `Ping` ボタンを押します。（まだ使えないボタンは薄く表示され、その下の文で理由が分かります。）

#### 観察ポイント

- キャンバス上を飛び回るパケット（丸いアニメーション）を追ってみましょう。
- 最初に **ARP Request** が飛ぶことに注目してください（次のホップのMACアドレスを知るため）。
- 正常に届けば `echo-reply` が返ってきます。

#### よくある失敗パターン

| エラーログ | 原因 | 対処 |
|----------|------|------|
| `No Gateway` | ゲートウェイが未設定 | デザインモードでGatewayを設定 |
| `TTL Expired` | ルーターを通りすぎた（ループの可能性） | 経路設定を見直す |
| `Host Unreachable` | ルートが見つからない | ルーターのインターフェース設定を確認 |

### 3.2 UDP送信（L4メッセージング）

**UDPとは**: 送りっぱなしの通信です。確認応答がなく、高速ですが信頼性は低いです。  
動画ストリーミングや音声通話など、少し欠けても問題ない用途に使われます。

#### 操作手順

1. 送信元ノードを選択します。
2. 「宛先」に、宛先の**IPアドレス**と**ポート**（例: `8080`）を入力します。
3. 「メッセージ」欄（UDPとTCPで共通）にメッセージを入力します。
4. UDPの欄で `UDP送信` ボタンを押します。

#### 観察ポイント

- 受信先のノードがそのポートを**受信待機（Listen）していない**場合、`ICMP Port Unreachable`（ポート到達不能）エラーが返ってきます。
- 受信待機しているサーバーを使う場合は、デザインモードで「サービス」タブからポートを開放してください。

> **注意（RFC準拠）**: マルチキャスト（`224.x.x.x`）宛てのUDPパケットは、ポートが閉じていても **ICMPエラーを返しません**。これは、大量のエラーでネットワークが溢れることを防ぐためのルールです（RFC 1122）。

### 3.3 TCP通信（3-way ハンドシェイク）

**TCPとは**: 「接続を確立してからデータを送る」信頼性の高い通信です。  
WebブラウザやメールなどはこのTCPを使っています。

#### 操作手順

1. 送信元ノードを選択します。
2. 「宛先」に、宛先のIPアドレスとポート（例: `80`）を入力します。
3. TCPの欄で **① 接続** を押してハンドシェイクを始めます。タイトルの横の状態が、○ 未接続 → ◐ 接続中… → ● 接続済み と変わります。
4. 接続できると **② 送信** と **③ 切断** が押せるようになり、① 接続は薄くなります。切断が終わると、状態は未接続に戻ります。

#### 通信の流れ（3-way ハンドシェイク）

```
PC（クライアント）          サーバー
      │                       │
      │── SYN ──────────────>│  「接続したいです」
      │<─ SYN-ACK ──────────│  「了解しました」
      │── ACK ──────────────>│  「接続確立！」
      │                       │
      │== ESTABLISHED (通信開始) ==
      │                       │
      │── TCP Send ──────────>│  データ送信
      │                       │
      │── FIN ──────────────>│  「切断したいです」
      │<─ FIN-ACK ──────────│  「了解しました」
```

## 第4章　ネットワークサービス

### 4.1 DHCP（IPアドレス自動取得）

**DHCPとは**: 「自動でIPアドレスをもらう」仕組みです。  
家のWi-Fiにつないだとき、自動でIPアドレスが振られるのはDHCPのおかげです。

#### 事前準備（デザインモード）

DHCPサーバーを配置し、以下を設定します。
- **IP Pool（配布範囲）**: 例 `192.168.1.100` 〜 `192.168.1.200`
- **Lease Time**: IPを貸し出す期間
- **Gateway/DNS**: クライアントに渡す情報

#### 操作手順（DORAプロセス）

1. IPアドレスが `0.0.0.0` のPCを選択します。
2. `DHCP Renew` ボタンを押します。

#### DORAの流れ

```
PC                               DHCPサーバー
 │── DISCOVER (broadcast) ──────>│  「誰かIPくれますか？」
 │<─ OFFER ───────────────────── │  「192.168.1.100どうぞ」
 │── REQUEST (broadcast) ──────> │  「じゃあそれをもらいます」
 │<─ ACK ──────────────────────  │  「確定しました！」
```

> **ポイント**: DHCP通信はブロードキャスト（全員への送信）です。そのため、ルーターを越えては届きません（TTL=1）。DHCPサーバーはクライアントと同じL2セグメント（同じスイッチ配下）に置く必要があります。

### 4.2 mDNS Query（マルチキャストDNS）

**mDNSとは**: DNSサーバーなしで、ネットワーク上のホスト名を解決する仕組みです。  
Appleの「Bonjour」や、プリンターの自動検出などに使われています。

#### 操作手順

1. 検索したいノードを選択します。
2. 左ペインの「NETWORK SERVICES」から `mDNS Query` を押します。

#### 通信の流れ

```
PC                           グループ 224.0.0.251
 │── mDNS Query (multicast) ───────────────────>│
 │                                               │
 │                          応答するサーバー
 │<─ mDNS Response (unicast) ─────────────────  │
```

> **条件**: 応答するノードは「mDNS RESPONDER」が **ENABLED** に設定されている必要があります。また、そのノードが `224.0.0.251` グループに参加していることが前提です。

### 4.3 ファイアウォール（ルーター）

ルーターは**ファイアウォール**で、一部の通信を止められます。ルーターを選び、**ファイアウォール**欄を開きます。

- 1つのルールは、動作（**許可** / **拒否**）、プロトコル（すべて / ICMP / TCP / UDP）、送信元、宛先、TCP/UDPのときはポートで構成されます。送信元と宛先には、`any`、アドレス（`192.168.1.10`）、ネットワーク（`192.168.1.0/24`）を指定できます。
- ルールは**上から順に**調べ、**最初に一致したもの**が適用されます。矢印で順番を変えられます。
- 一覧の最後の**どのルールにも一致しない**行で、どれにも一致しないときの動作を選びます。既定は**許可**なので、ルールが無いルーターは、これまで通りに動きます。**拒否**にすると、明示的に許可した通信以外はすべて止まります（実機と同じ「暗黙の拒否」）。
- 拒否されたパケットは**黙って捨てられ**、エラーは返りません。送信側にはタイムアウトだけが見えます。どのルールで拒否したかは、ログで分かります。
- 調べるのは、ルーターが**転送する**通信だけです。ルーター自身宛ての通信は対象外です。
- ファイアウォールは**ステートレス**です。戻りの通信も、別のパケットとして調べます。既定を拒否にして `PC 1 → PC 2` だけを許可すると、戻りの `PC 2 → PC 1` は止まります。往復の両方を許可してください。
- 問題のあるルール（たとえばICMPにポートを指定した場合）は、説明が表示され、直すまで**無視**されます。

サンプル「6. ファイアウォールでpingを止める」で試せます。

### 4.4 NAT（ルーター）

**NAT** は、内側のネットワークにある多数の機器が、外側では**1つのアドレス**を共有できるようにする仕組みです。家庭用ルーターが行っているもので、家の中のすべての機器が、ルーター1つのアドレスでインターネットに出ています。

#### 設定方法

ルーターを選ぶ → **NAT** 欄を開く → **外側ポート**（インターネット側のポート）を選ぶ → **NATを有効にする** にチェックを入れます。それ以外のポートは、すべて**内側**として扱われます。外側ポートには、IPアドレスが必要です。

#### 動き

1. 内側の機器が、外側へパケットを送ります（例: `192.168.1.10:50001` → サーバー `203.0.113.10:80`）。
2. ルーターは、**送信元のアドレスとポート**を、自分の外側のアドレスと**新しいポート**（`203.0.113.1:40000`）に書き換え、その対応を**変換表**に記録します。pingでは、ポートの代わりにICMPの識別子を使います。
3. サーバーは `203.0.113.1:40000` へ応答します。ルーターは変換表から該当の項目を探し、元の内側のアドレスとポートに戻して、応答を転送します。

```
PC 1 192.168.1.10:50001 ─► ルーター ─► 203.0.113.1:40000 ─► サーバー 203.0.113.10:80
PC 1 192.168.1.10:50001 ◄─ ルーター ◄─ 203.0.113.1:40000 ◄─ サーバー
```

- 2台のPCが、同じ内側のポートを同時に使っても、外側のポートは別々に割り当てられるので、混ざりません。
- 外側から届いた通信のうち、**応答ではないもの**（変換表に対応する項目が無いもの）は**破棄**され、ログに記録されます。ルーターの外側のアドレス宛てでも、内側のアドレスへ直接送っても同じです。NATの内側の機器に、外から直接つながらないのは、このためです（ルーター自身のアドレスへのpingには、ルーターが応答します）。
- 変換表は**64件**まで保持し、超えると古いものから消えます。ごみ箱ボタンで全消去できます。ルーターのケーブルを抜いたとき、内側の機器を削除したときも、関係する項目が消えます。変換表は保存されません。
- ファイアウォールのルールは、**内側のアドレス**で判定されます（行きは書き換える前、戻りは元に戻したあと）。
- NATが扱うのは**ユニキャスト**の通信だけです。マルチキャストとブロードキャストは、NATでは書き換えも破棄もされません。
- 対象外: ポート転送、ICMPエラーメッセージの変換、使われない項目の時間切れ。

サンプル「7. NATで内側のPCを外に出す」で試せます。サーバーには `192.168.1.0/24` への経路がありませんが、応答は届きます。NATを無効にして、もう一度 ping すると、違いが分かります。

### 4.5 VLANとトランクポート（スイッチ）

**VLAN** は、1台のスイッチを、別々のネットワークに分けます。VLANが違う機器どうしは、IPアドレスが同じネットワークにあっても、スイッチを通して通信できません。

#### ポートの種類

スイッチを選び、**ポートのVLAN** 欄を開きます。ポートは、次のどちらかです。

- **アクセス**: **1つのVLAN**（1〜4094）に属します。ホストをつなぐポートです。すべてのポートは、最初はVLAN 1のアクセスなので、設定しないスイッチは、これまでどおりに動きます。
- **トランク**: **すべてのVLAN**を、1本のケーブルで運びます。各フレームに**VLANタグ**を付けて、反対側がどのVLANのフレームかを分かるようにします。スイッチ間に使います。

#### フレームの動き

1. フレームのVLANは、**スイッチに入ったところ**で決まります。アクセスポートは、そのポートのVLANにし、トランクポートは、タグから読み取ります。
2. スイッチは、**同じVLAN**のポート（とトランク）にだけ送ります。フラッド、MAC学習、IGMPスヌーピングも、すべてVLANの中に閉じるので、MAC表はVLANごとに別々です。
3. アクセスポートから出るときは、タグを外し、トランクから出るときは、タグを付けます。ホストには、タグは見えません。

決まりに反するフレームは、破棄されて、ログに記録されます。アクセスポートが受けられるのはタグ無しだけ、トランクポートが受けられるのはタグ付きだけです。

#### 警告が出る間違い

設定欄のポートに、次の場合は警告が出ます。
- ケーブルの両端が、**違うVLANのアクセスポート**: フレームは、反対側のスイッチでは、そのポートのVLANとして扱われ、VLANが混ざります。
- 片方が**アクセス**、もう片方が**トランク**: フレームは破棄されます。
- **トランク**が、PC・サーバー・ルーターにつながっている: これらはVLANタグを扱えません。

VLANを使っているスイッチでは、ポートがVLANごとにまとめて表示され、MAC表とIGMP表の各行に、VLAN番号が付きます。

#### マルチキャスト（IGMP v2）

グループの表、ルーターポート（mrouter）、**クエリア**は、**VLANごと**に持ちます。クエリアは、自分のポートがあるすべてのVLANにクエリを送ります（トランクではタグ付き）。VLAN 1では、管理IPをアドレスとして使い、それ以外のVLANでは、アドレスを持たない（0.0.0.0）ため、実際のアドレスを持つスイッチが、そこでの選挙に勝ちます。トランクの上で受けたLeaveでは、登録を消しません。トランクは多くの受信者を代表しているので、時間切れで消えます。

サンプル「8. VLANとトランク」で試せます。対象外: 許可VLANの一覧、ネイティブVLAN、STP、VLAN間のルーティング。

## 第5章　マルチキャストと IGMP

### 5.1 マルチキャストとは

**マルチキャスト**は「特定のグループに登録した全員に同時配信する」通信方式です。

| 通信方式 | 宛先 | 例 |
|----------|------|-----|
| ユニキャスト | 1対1 | 電話 |
| ブロードキャスト | 全員 | ラジオ |
| **マルチキャスト** | グループのメンバー全員 | 有料チャンネル |

### 5.2 マルチキャストグループへの参加（Join）

マルチキャストを**受け取る**には、まずそのグループに参加（Join）する必要があります。  
送る側はグループに参加していなくても送信できます（テレビ局は自分でテレビを見なくてもよい）。

#### 操作手順

1. グループに参加させたいノードを選択します。
2. 左ペインの「MULTICAST GROUP」欄にグループアドレス（例: `224.2.2.2`）を入力します。
3. `Join` ボタンを押します。
4. ノードの下に **「JOINED GROUPS」** という黄色いバブルが表示されれば成功です。

> **裏側で何が起きているか**: `Join` を押すと、裏側では **IGMP Membership Report** パケットが自動的にスイッチに送信されます。これによりスイッチが「このポートの先にグループのメンバーがいる」と学習します。

### 5.3 グループから退出（Leave）

1. 同じパネルで `Leave` ボタンを押すと、グループから退出します。
2. スイッチのIGMP Snoopingテーブルからも自動的に削除されます。

### 5.4 IGMP Snoopingの観察

スイッチがマルチキャストパケットを「賢く転送」するために行うのが **IGMP Snooping**（IGMPスヌーピング）です。

#### 確認方法

1. ノード（Join済み）から先のスイッチを確認します。
2. スイッチの下に **「IGMP SNOOPING TABLE」** テーブルが表示されます。
3. グループアドレスと、そのグループに参加しているポートおよび残り生存時間が一覧表示されます。

```
┌────────────────────────────────────────┐
│         IGMP SNOOPING TABLE            │
│  Router Port: eth2  (expires in 58s)   │
│  224.2.2.2                             │
│    └─ eth0  (expires in 27s)           │
│  224.0.0.251                           │
│    └─ eth1  (expires in 14s)           │
└────────────────────────────────────────┘
```

> **なぜ重要か**: IGMP Snoopingがなければ、マルチキャストパケットは全ポートにブロードキャストされてしまいます（ネットワークが混雑する）。スヌーピングにより、必要なポートだけに転送することで効率化しています。

---

### 5.5 スイッチの管理IP（Management Interface）

スイッチには、VLAN 1インターフェース用の**管理IPアドレス**を設定できます。

#### 設定方法

スイッチをクリック → **「SWITCH IGMP CONFIG」** パネルを開く → **Management Interface (VLAN 1)** セクションに入力します。

| 設定項目 | 説明 | 例 |
|----------|------|----|
| IP Address | スイッチ管理用IPアドレス | `192.168.1.254` |
| Subnet Mask | 管理インターフェースのサブネットマスク | `255.255.255.0` |

#### ポイント

- 管理IPが未設定の場合、**「UNMANAGED L2 SWITCH」** と表示され、単純なL2転送機器として動作します。
- 管理IPを設定すると、**「MANAGED L2 SWITCH」** に変わります。
- **管理IPのサブネットは、ノード（PC等）のサブネットと異なっていても問題ありません。**  
  例えば、スイッチが `10.0.0.0/24`、PCが `192.168.1.0/24` でも、PC間のL2転送（データプレーン）にはまったく影響しません。  
  これは「管理プレーン（コントロールプレーン）」と「転送プレーン（データプレーン）」が独立しているというネットワーク設計の基本原則を示しています。
- IGMP Querier機能を有効にするには、管理IPの設定が必須です。

---

### 5.6 IGMP Snooping — 詳細設定

#### Snoopingの有効・無効

| 状態 | 動作 |
|------|------|
| **ENABLED**（デフォルト） | グループメンバーシップを学習し、登録ポートにのみマルチキャストを転送 |
| **DISABLED** | 全ポートにマルチキャストをフラッディング（Hubと同等の動作） |

#### Snooping Aging Time（エージングタイム）

Snoopingテーブルに登録されたエントリ（ポート）の**生存時間（TTL）**です。  
タイマーが0になってリフレッシュされない場合、そのポートはグループから自動削除されます。

| パラメータ | デフォルト | 設定可能範囲 |
|------------|------------|------------|
| Snooping Aging Time | 30秒 | 5〜300秒 |

IGMP Snoopingが有効な状態で、**SWITCH IGMP CONFIG** パネルから値を変更できます。

#### 重要：未登録マルチキャストは「届かない」（厳格破棄モード）

> このシミュレータは **RFC 4541 Approach B（厳格なマルチキャストフィルタリング）** を実装しています。
>
> IGMP Snoopingが **ENABLED** の状態で、Snoopingテーブルに宛先マルチキャストグループの登録ポートが存在しない場合（未参加またはエージングアウトで消滅）、パケットは**即座に破棄（Drop）され、フラッディングはされません**。
>
> これは**意図的な仕様**です。以下のことを体験・理解できるように設計しています：
> - エントリが消えた瞬間に通信が途絶える様子を可視化できる。
> - 「Joinするだけでは不十分で、継続的なリフレッシュ（Querier）が必要」という事実を実感できる。
> - Querierがなぜ必要なのかを直感的に理解できる。
>
> **例外：リンクローカルマルチキャスト（`224.0.0.0/24`）は常にフラッディング**
> `224.0.0.1`（All Hosts）や `224.0.0.251`（mDNS）などは、RFC 4541の規定に従い、
> Snoopingテーブルに未登録であっても全ポートにフラッディングされます。
> これらはインフラ制御用のマルチキャストであり、フィルタリングしてはならないためです。

---

### 5.7 IGMP Querier（クエリア）

**IGMP Querier** は、全ポートに定期的に **IGMP General Query** を送信し、グループメンバーに対してメンバーシップの再報告を促す機能です。これにより、Snoopingテーブルのエントリが消滅するのを防ぎます。

#### 有効条件

- スイッチに**管理IP**が設定されていること。

#### 有効化手順

スイッチをクリック → **SWITCH IGMP CONFIG** → **IGMP Querier** を **ENABLED** にトグル。

#### クエリアの状態

| 状態 | 説明 |
|------|------|
| **Active** | このスイッチが代表クエリアとして定期的にGeneral Queryを送信中 |
| **Standby（選挙に敗北）** | より小さいIPを持つ別のクエリアがActive。このスイッチは送信を停止して待機中 |

#### Query Interval（クエリ送信間隔）

| パラメータ | デフォルト | 設定可能範囲 |
|------------|------------|------------|
| Query Interval | 60秒 | 5〜300秒 |

間隔を短くするとエントリのリフレッシュが速くなりますが、IGMPトラフィックが増加します。

#### クエリア選挙（Querier Election）

同じセグメントに複数のQuerierが存在する場合、自動的に1台の **Active Querier** が選出されます：

- **管理IPアドレスが最小のスイッチ** が選挙に勝ち、Active Querierになります。
- その他のスイッチは **Standby** に移行し、Queryの送信を停止します。
- これはRFC 2236で規定されているIGMPクエリア選挙の動作を忠実に再現しています。

#### 手動Query送出

**[Send General Query]** ボタンを押すと、クエリアの有効・無効に関わらず、スイッチの全ポートから即座にGeneral Queryを送出できます。テスト時にSnoopingテーブルを手動でリフレッシュしたい場合に便利です。

---

### 5.8 Router Port（mrouterポート）の学習

IGMP Snoopingが有効な場合、スイッチは**マルチキャストルーターまたはActive Querierに接続しているポート**を自動学習します。

- あるポートPからGeneral Queryが到着した場合、そのポートPが **mrouterポート** として登録されます。
- mrouterポートには、全グループのマルチキャストトラフィックが常に転送されます（ルーターはルーティング処理のために全マルチキャストを受信する必要があるため）。
- mrouterポートエントリの有効期限は `Aging Time × 2` 秒です。
- 現在のmrouterポートと残り生存時間は、キャンバス上の **IGMP SNOOPING TABLE** に表示されます。

---

### 5.9 学習シナリオ

#### シナリオ A — クエリアなしでのエージングアウト体験

1. スイッチ: **Snooping ON, Querier OFF**、Aging Time = **30秒**
2. PCがグループ `239.1.1.1` に参加（Join）→ Snoopingテーブルに30秒のカウントダウンつきでエントリが現れる。
3. IGMPトラフィックなしで30秒待つ。
4. エントリが消滅 → 以降 `239.1.1.1` 宛てのマルチキャストは**破棄（Drop）**され、PCに届かなくなる。

→ **学べること**: クエリアがいないと、Snoopingエントリはやがて期限切れになり、マルチキャスト配信が突然途絶える。

#### シナリオ B — クエリアによるメンバーシップ維持

1. スイッチ: 管理IP設定済み、**Snooping ON, Querier ON**、Query Interval = **15秒**、Aging Time = **20秒**
2. PCがグループに参加 → エントリが現れる。
3. 15秒ごとにスイッチがGeneral Queryを送信 → PCがReportを返答 → エントリのタイマーがリセット。
4. タイマーは0にならず、マルチキャスト配信が継続される。

→ **学べること**: クエリアが「ハートビート」として機能し、エントリを生かし続けることでマルチキャストが維持される。

#### シナリオ C — 複数スイッチのクエリア選挙

1. SwitchA（管理IP: `10.0.0.1`）とSwitchB（管理IP: `10.0.0.2`）を直結し、両方でQuerierをON。
2. IPが小さいSwitchAが **Active**、SwitchBが **Standby** になることを確認。
3. SwitchBはSwitchAからのQueryを受け取ったポートを **mrouterポート** として学習することを確認。
4. マルチキャストがmrouterポート経由で両スイッチをまたいで正しく転送される。

→ **学べること**: クエリア選挙によりQueryの重複送信を防ぎ、mrouterポート学習によって複数スイッチ環境のマルチキャスト中継が成立する。

## 第6章　学習用テーブルの読み方

通信が発生すると、各ノードの下に「学習した情報」が自動的に表示されます。

### 6.1 ARP TABLE（ARPテーブル）

- **表示ノード**: PC、サーバー、ルーター
- **内容**: IPアドレス ↔ MACアドレスの対応表
- **役割**: 「IPアドレスは知っているが、実際にパケットを届けるにはMACアドレスが必要」な場合に参照される

```
┌────────────────────────┐
│       ARP TABLE        │
│  192.168.1.1 → AA:BB  │  ← ゲートウェイのMACアドレス
│  192.168.1.11 → CC:DD │  ← 同じサブネット内のPCのMACアドレス
└────────────────────────┘
```

> **用語解説（ARP）**: Address Resolution Protocol の略。IPアドレスからMACアドレスを調べるプロトコル。「192.168.1.10 は誰ですか？」とブロードキャストで問い合わせ、本人が「私のMACアドレスは〇〇です」と返答する。

### 6.2 MAC TABLE（MACテーブル）

- **表示ノード**: スイッチ
- **内容**: MACアドレス → ポート番号の対応表
- **役割**: どのポートの先にどのMACアドレスの機器がいるかを記録し、効率よく転送する

```
┌────────────────────────┐
│       MAC TABLE        │
│  AA:BB:CC → eth0       │  ← eth0の先にAA:BB:CC がいる
│  DD:EE:FF → eth1       │
└────────────────────────┘
```

> **なぜ必要か**: スイッチはMACテーブルがないと全ポートにパケットをコピー（フラッド）してしまいます。MACを学習することで、必要なポートだけに転送できるようになります。

### 6.3 DNS CACHE（DNSキャッシュ）

- **表示ノード**: PC、サーバー
- **内容**: ホスト名 → IPアドレスの変換結果のキャッシュ
- **役割**: 一度解決した名前を記憶しておくことで、次回の通信を高速化する

```
┌────────────────────────────────┐
│          DNS CACHE             │
│  server1.local → 192.168.2.20 │
└────────────────────────────────┘
```

### 6.4 JOINED GROUPS（参加中のマルチキャストグループ）

- **表示ノード**: PC、サーバー
- **内容**: 現在参加しているマルチキャストグループのIPアドレス一覧

```
┌──────────────────────┐
│    JOINED GROUPS     │
│    224.0.0.251       │  ← mDNSグループ
│    224.2.2.2         │  ← カスタムグループ
└──────────────────────┘
```

## 第7章　PACKET LOGS（パケットログ）の読み方

画面下部のパケットログには、発生した通信イベントが時系列で表示されます。

### 1行の読み方

パケットログは、シミュレーションモードでキャンバスの下に表示されます。1件のイベントが**1行**で、時刻 | 状態 | プロトコル | 送信元 → 宛先 | 内容 の順に並びます。行をクリックすると全文が表示され、マウスを重ねるとツールチップでも読めます。

| 状態の記号 | 意味 |
|-----------|------|
| **↑ 送信** (青) | パケットが送信された |
| **↓ 受信** (緑) | パケットが受信された |
| **✖ エラー** (赤) | エラーが発生した（パケット到達不能、ポート未開放など） |
| **⊘ 破棄** (灰) | パケットが意図的に破棄された（マルチキャストグループ未参加、L2フィルタなど） |

### パネルの使い方

- **高さの変更**: パネル上端をドラッグします。**開閉**: 左端の矢印で行います。どちらも記憶されます。
- **絞り込み**: プロトコル（ARP、ICMP など）を選ぶと、その行だけが表示されます。
- 直近200件を、新しいものが上になるよう保持します。

## 第8章　トラブルシューティングガイド

通信が失敗したとき、以下のチェックリストを順番に確認してください。

### ✅ L2（物理・MACアドレス）のチェック

- [ ] リンク（ケーブル）は正しくつながっているか？
- [ ] スイッチのMACテーブルに宛先MACが学習されているか？

### ✅ L3（IPアドレス・ルーティング）のチェック

- [ ] 送信元と宛先のIPアドレスは同じサブネットか？（違う場合はゲートウェイが必要）
- [ ] ゲートウェイのIPアドレスは正しく設定されているか？
- [ ] ゲートウェイのIPアドレスは自分と同じサブネット内にあるか？
- [ ] ルーターの両側にIPアドレスが正しく設定されているか？

### ✅ 「要求がタイムアウトしました」

pingに応答がないとき、ログに **要求がタイムアウトしました: … から応答がありません** と出ます。DNSサーバーが応答しないときも同じです。次の順で確認してください。宛先のIPアドレス、サブネットマスク、ゲートウェイ(別のネットワークへ出る場合)、ケーブル。設定パネルでも、疑わしい値は赤で示されます。

### ✅ L4（ポート）のチェック

- [ ] 宛先サーバーで、接続しようとしているポートが開いているか？（TCPポート開放設定）

### ✅ マルチキャスト特有のチェック

- [ ] 受信側のノードは対象グループに参加（Join）しているか？
- [ ] `mDNS RESPONDER` は ENABLED になっているか？

### よくある間違いと正しい設定

#### ❌ 間違い: ゲートウェイがサブネット外
```
PC:      IP=192.168.1.10  Mask=255.255.255.0  GW=10.0.0.1  ← 10.x.xはサブネット外
```

#### ✅ 正しい設定
```
PC:      IP=192.168.1.10  Mask=255.255.255.0  GW=192.168.1.1  ← 同じ /24 内
Router:  IP=192.168.1.1（LAN側）/  10.0.0.1（WAN側）
```

## 付録A：主要プロトコルまとめ

| プロトコル | 階層 | 用途 | RFCの参考番号 |
|-----------|------|------|--------------|
| ARP | L2/L3境界 | IPからMACを解決 | RFC 826 |
| ICMP | L3 | 疎通確認・エラー通知 | RFC 792 |
| IGMP | L3（マルチキャスト制御） | グループ管理 | RFC 1112, RFC 2236 |
| UDP | L4 | 軽量・高速なデータ転送 | RFC 768 |
| TCP | L4 | 信頼性の高いデータ転送 | RFC 793 |
| DHCP | L7（UDP上） | IP自動割り当て | RFC 2131 |
| DNS | L7（UDP/TCP上） | 名前解決 | RFC 1035 |
| mDNS | L7（UDP/マルチキャスト） | ローカル名前解決 | RFC 6762 |
